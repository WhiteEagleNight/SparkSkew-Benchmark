# 设计决策记录

本文记录了项目中 17 个有争议的技术选型。每个决策都梳理了背景、备选方案和最终取舍，方便后续 Review 或重构时快速对齐上下文。

---

## 1. 运行时：使用项目内的便携 JDK 17，而非系统环境

**背景**：本机仅安装了 Java 21，但 Spark 3.5.1 官方支持的最高版本为 JDK 17。

**备选方案**：
- 修改系统 `JAVA_HOME`，降级 Java 版本；
- 使用项目内便携的 Temurin JDK 17；
- 强行使用 Java 21 运行 Spark。

**最终选择**：使用便携 JDK 17。在 `spark_jobs/common.py:38` 的 `configure_runtime()` 中优先加载 `.bootstrap/jdk17/jdk-17*`。

**原因**：避免污染用户的系统环境，同时保证在不同机器上都能一键复现。如果使用 Java 21 强行运行，容易遇到 `InaccessibleObjectException` 或序列化不兼容的异常，且这类错误往往在运行中途才暴露，排查成本较高。

**代价**：需要额外下载约 180MB 的 JDK，且 `.bootstrap/` 被列入 `.gitignore`。新克隆项目时需要自行准备 JDK 17，此点已在 README 中注明。

## 2. 数据规模：坚持生成 100 万行，不采取降级方案

**背景**：硬性要求为 100 万行，且热门商品占比 ≥35%。

**备选方案**：
- 仅生成 20 万行，并在文档中说明降级情况；
- 直接生成 100 万行；
- 生成 100 万行，但仅对采样数据执行 Benchmark。

**最终选择**：直接生成 100 万行。

**原因**：本机资源足以支撑。生成耗时约 11.598 秒，CSV 文件大小约 43MB。只有达到百万级数据量，Shuffle 行为才具备可观测性。如果降级，Benchmark 将失去意义；如果对采样数据测试，会导致 DWD/DWS 的断言数据与 Benchmark 输入不一致。

**代价**：全量运行一次 Pipeline 约需 1 分钟，ALS 评估约需 10 分钟，且原始 CSV 不提交至 Git。

*(实测结果：热门商品 380,421 行，占比 38.04%。)*

## 3. ODS 层：保留原始字符串，不在接入层转换类型

**背景**：CSV 接入后，是否应立即将 ID 和时间转换为 Int 与 Timestamp？

**备选方案**：
- 在 ODS 层直接转换为强类型；
- 全量保存为 String，交由 DWD 层处理；
- 使用 Spark 的 `inferSchema`。

**最终选择**：全量保存为 String。

**原因**：ODS 层的职责是保留最原始的数据快照。如果后续发现清洗逻辑有误，可以直接基于原始字符串重放。若在 ODS 层强转，一旦出错将丢失原始值；且 `inferSchema` 面对脏数据会静默生成 Null 值，同时还会增加一次文件扫描开销。

**代价**：DWD 层必须显式处理类型转换与过滤，ODS 存储空间会略大（在当前 Demo 场景下可接受）。

---

## 4. DWD 层：静态全量覆盖，不使用动态分区覆盖

**背景**：DWD 按 `dt` 分区，重新运行时如何避免旧分区数据残留？

**备选方案**：
- 静态全量 Overwrite；
- 开启 `partitionOverwriteMode=dynamic`，仅覆盖新产生的分区；
- Append + 主键 Merge。

**最终选择**：静态全量覆盖。`dwd_build.py:117` 中固化了 `mode("overwrite")`。

**原因**：本项目为批处理 Demo，DWD 数据完全由 ODS 推导。全量覆盖能保证数据的幂等性，避免产生“本次未产出某个 dt，旧数据仍然保留”的混合快照。动态覆盖容易导致脏数据残留；主键 Merge 需要引入增量窗口，复杂度较高。

**代价**：每次需重算 100 万行（约 1 分钟）。在生产环境中，通常会改为有界重处理 + 动态覆盖 + Merge 策略。

---

## 5. DWD 层：强制执行去重与质量断言

**背景**：虽然生成器保证了主键唯一，DWD 层是否仍需执行去重与校验？

**备选方案**：
- 信任源数据，跳过检查；
- 仅校验数据量是否大于 0；
- 主键去重 + 非空率 + 唯一性 + 持久化一致性校验。

**最终选择**：全套去重与 4 项断言（`dwd_build.py:82-127`）。

**原因**：断言属于数据契约的一部分。如果源 CSV 发生变更或上游发生重复投递，任务应直接报错中断，而非产出静默的异常数据。断言中的第 4 项（持久化行数一致性）能有效拦截“写入成功但读取缺失”的存储问题。

**代价**：`dropDuplicates` 会触发 Shuffle 开销，但百万级数据量完全可以支撑。0.999 的非空率阈值是显式配置：允许极少量缺失，但拒绝系统性空值。

## 6. 聚合对比：三种方案使用同样的逻辑两阶段，控制 salt scope

**背景**：对比加盐效果时，Baseline 应采用单阶段 `groupBy` 还是两阶段？

**备选方案**：
- Baseline 单阶段，加盐版本两阶段；
- 三种方案都写成逻辑两阶段，treatment 是 `salt_scope`（none / all / hot_only）；
- 双方均单阶段，仅对比加盐表达式。

**最终选择**：三种方案都写成逻辑两阶段（`skew_aggregation.py` 的`build_item_stats()`）。

**原因**：如果 Baseline 使用单阶段，测得的差异会混入“有没有第二阶段”这个结构性差异。固定逻辑聚合形状后，至少业务口径一致：都是先算部分指标，再恢复 `item_id`。

**需要说清楚的边界**：这不代表物理计划只差一个布尔位。不加盐的两次 `groupBy("item_id")` 可能被 Catalyst 合并为一次 shuffle；加盐方案在本写法下会 shuffle 两次，因为 stage-1 的 key 是 `(item_id, _salt)`，stage-2 才恢复 `item_id`，通常无法享受同 Key 两阶段聚合的合并。这次额外 shuffle 是加盐的真实成本，benchmark 会明确报告 stage 数、shuffle 字节和 group 基数，不把它伪装成“只改了一个变量”。*(实测结果：即便在同样的逻辑两阶段下，全量加盐和仅热点键加盐都更慢；该结论只覆盖本项目负载和本实现。详见第 15、17 条及 Benchmark 章节。)*

## 7. 盐值生成：采用确定性 Hash，禁用 `rand()`

**背景**：Salt 应当随机生成，还是基于行内容计算？

**备选方案**：
- 使用 `rand()` 随机生成；
- 使用 `xxhash64(user_id, behavior_type, event_time) % N` 计算；
- 仅使用 `user_id % N`。

**最终选择**：基于 `xxhash64` 计算（`skew_aggregation.py:73-91`）。

**原因**：重新运行必须保证盐值分配一致，否则 Benchmark 的多次运行结果无法对比，DWS 对账也会失败。`rand()` 每次运行结果不同；仅依赖 `user_id` 无法解决“单用户高频访问热门商品”导致的倾斜问题。引入 `event_time` 能有效提高基数，将同一用户的行为打散。

**代价**：每行增加一次 Hash 计算，在百万级数据量下开销可忽略。

## 8. 指标采集：使用 JVM SparkListener 获取真实耗时

**背景**：PySpark 3.5 未提供 Python 侧的 Listener，如何获取最长的 Task 耗时？

**备选方案**：
- 仅记录总耗时；
- 依赖 Spark UI 手动观察；
- 编写 Java Listener 并编译为 Jar 挂载。

**最终选择**：编写 Java Listener（`TaskTimingCollector.java`），在 `benchmark_skew.py:84` 的 `ensure_listener_jar()` 中按需编译。

**原因**：总耗时无法反映是否存在长尾 Task。手动查看 UI 无法自动化，也无法写入 JSON。通过挂载原生 Listener，可以精确获取 `TaskInfo.duration()` 及 Shuffle 的读写量。

**代价**：首次运行需要 `javac` 与 `jar` 环境。如果编译失败，Benchmark 仍可运行，但会将 `collection_method` 标记为 `fallback_total_time_only`，且绝不伪造 Task 数据。

## 9. Benchmark 触发：使用 `collect()` 替代 `count()`

**背景**：测试两阶段聚合时，应使用何种 Action 触发计算？

**备选方案**：
- 使用 `aggregate.count()`；
- 使用 `aggregate.collect()`；
- 使用 `aggregate.write.parquet()`。

**最终选择**：使用 `collect()`（`benchmark_skew.py:199-205`）。

**原因**：Catalyst 的 Count 优化会跳过部分聚合与投影阶段，导致两阶段计划未完整执行。`collect()` 能将 20,000 行的完整指标拉回 Driver，确保物化。而写 Parquet 会将磁盘 I/O 开销引入对比。

**代价**：Driver 需要接收两万行数据。若数据规模达千万级，应改用写盘配合 `count()` 校验的策略。

## 10. 数据切分：按时间 80% 分位切分，不使用随机 Split

**背景**：ALS 的训练集与测试集应如何切分？

**备选方案**：
- 使用 `randomSplit(0.8, 0.2)`；
- 按 `event_time` 的 80% 分位切分；
- 按用户切分（留出部分用户）。

**最终选择**：按时间切分（`evaluate_als.py:81`）。

**原因**：推荐系统的核心是利用历史预测未来。随机切分会将未来的交互行为泄漏至训练集，导致指标虚高。按用户切分则会改变冷启动的定义。按时间切分最贴合真实上线场景，并能自然生成“测试期才出现”的冷启动用户。

**代价**：测试集数据分布可能存在漂移；冷启动用户无法被 ALS 评分，必须单独提取评估。*(实测测试集占比 20.0093%，冷启动用户占比 11.0978%)。*

## 11. 模型评估：隐式 ALS + 排序指标，不计算 RMSE

**背景**：日志中仅有 pv/cart/fav/buy 行为，无 1-5 星评分，如何进行训练与评估？

**备选方案**：
- 将 buy 映射为 5 分，cart 映射为 3 分，强制计算 RMSE；
- 将行为加权为隐式置信度，计算 NDCG/MAP 等指标；
- 直接基于热门商品排序兜底。

**最终选择**：隐式 ALS + `RankingMetrics`。

**原因**：隐式反馈缺乏负样本，用户未点击不代表负面评价（可能仅仅是没有曝光）。强制计算 RMSE 会使得指标失去业务意义。排序指标能真实反映“推荐列表前 K 个商品是否命中了后续行为”。**文档中已明确标注：隐式反馈不适用 RMSE，因此本项目不输出 RMSE。**

**代价**：无法报告 RMSE；必须处理冷启动与已见商品过滤；`rating` 的语义从评分转变为置信度。

---

## 12. 评估过滤：剔除冷启动用户与已见商品

**背景**：测试集中的用户与商品可能在训练集中未曾出现，评估时如何处理？

**备选方案**：
- 包含所有测试用户，推荐列表不做过滤；
- 剔除训练未见用户，剔除已推荐商品，并单独报告冷启动比例；
- 仅评估 buy 行为。

**最终选择**：剔除冷启动与已见商品，并单独报告比例。

**原因**：ALS 无法为训练未见过的用户打分，强行评估会导致无效结果；推荐已见商品本质是“记忆”，而非“泛化推荐能力”。单独报告冷启动比例，能避免将困难样本静默丢弃的误导。

**代价**：评估用户数从 45,054 降至 33,528。冷启动采用的流行度兜底策略与 ALS 属于不同 cohort，指标不可直接横向对比，需在文档中明确说明。

## 13. 特征工程：独立构建，不输入 ALS

**背景**：行为序列特征应在训练窗口内构建，还是基于全量数据构建？

**备选方案**：
- 仅在训练窗口内构建，输入 ALS；
- 基于全量 DWD 构建，作为独立特征表，不输入 ALS；
- 基于全量构建，直接拼入 ALS 训练特征。

**最终选择**：全量构建，保持独立。

**原因**：若使用全量 DWD 构建特征输入 ALS，会导致严重的数据泄漏（引入未来信息）。当前的用户特征表（17 维）与商品特征表（10 维）主要用于探索及后续内容侧模型构建。

**代价**：若未来引入监督式冷启动模型，必须在训练时间窗内重建特征，当前的特征表无法直接复用。

## 14. 看板展示：读取离线 JSON，不在页面内运行 Spark

**背景**：Streamlit 看板应如何获取复杂的计算结果？

**备选方案**：
- 在页面内启动 `SparkSession` 实时计算；
- 读取离线生成的 JSON 产物；
- 将数值硬编码在页面代码中。

**最终选择**：读取离线 JSON。

**原因**：前端看板不应承担重型计算任务，需保证快速响应。读取 JSON 能确保页面展示数据与命令行产物完全一致，具备可审计性。硬编码方式会导致数据更新后页面失效。

**代价**：运行新实验后需要刷新页面（已配置 `st.cache_data(ttl=5)`）。首次 Clone 项目且未运行 Pipeline 时，页面仅显示缺失提示。

## 15. 负结果：加盐导致性能下降，如实记录

**背景**：Benchmark 实际结果显示，全量加盐版本的 Wall Clock 增加了 44.77%，最长 Task 增加了 85.53%（2026-11-08 的 measured run），与“加盐优化倾斜”的常规认知相悖。

**备选方案**：
- 调整参数，直到得出正向收益的结果；
- 如实保留数据，并解释 Map 端预聚合（Combine）的影响；
- 忽略该指标，仅报告功能实现。

**最终选择**：如实保留数据并解释原因。

**原因**：在 `count/sum` 这类支持 Map 端 Combine 的负载下，本实现里的加盐会导致净开销为正。如实记录该结论，能体现对 Spark 底层机制的理解深度。在技术评审中，能够清晰解释“加盐失效原因”远比单纯背诵优化理论更有价值。

**统计口径**：每种方案只有 1 个进入统计的 measured sample（第 2 次运行，第 1 次仅预热），所以 +44.77% / +85.53% 是**单次运行的差异**，没有重复采样、置信区间或显著性检验。Shuffle records、group 基数、Task 数是确定性结构指标，方向比 wall clock 百分比更可靠。该负结果只覆盖本项目这份 1M 行、38.04% 热 key、`count/sum`、`local[8]` 负载，不能外推为“加盐对所有可 Combine 负载都是负优化”。

## 16. DWS 默认路径：不加盐，加盐仅作演示/回归

**背景**：Benchmark 实测显示，在当前 100 万行、38.04% 热 key、`count/sum` 聚合上，全量加盐和仅热点键加盐都比不加盐慢；本次 measured run 中全量加盐 wall clock +44.77%、最长 Task +85.53%（单样本，见第 15 节统计口径）。但 `dws_build.py` 早期固定 `salted=True`，形成了“benchmark 说更慢、主链路却默认使用”的决策裂缝。

**备选方案**：
- DWS 继续固定加盐，仅靠文档解释“演示用”；
- DWS 默认不加盐，`--salted` 作为显式演示/回归入口；
- 同时产出两张 DWS 表，分别标记 salted/unsalted。

**最终选择**：DWS 默认不加盐；`spark_jobs/dws_build.py --salted` 和 `spark_jobs/run_pipeline.py --salted` 保留加盐参考路径。

**原因**：DWS 的聚合是 `count/sum/min/max`，支持 map-side Combine；benchmark 的负结果可以直接迁移到这个主链路。默认路径应服从实测证据，而不是为了展示技术而选择更慢的实现。加盐实现仍有价值：它可用于演示两阶段 key 恢复、做回归测试，以及未来迁移到不可 Combine 的聚合/热 key Join。

**代价**：默认路径不再展示加盐；需要单独运行 `--salted` 才能验证该实现。两条路径输出相同的 20,000 行、`sum(event_count)=1,000,000`，并执行相同的四条对账断言。

## 17. 选择性加盐与盐桶 sweep：把“只打热点”从建议变成实测

**背景**：如果只比较“不加盐”和“全量加盐”，读者无法判断加盐的高开销有多少来自“把所有 item 都拆开”，多少来自“多一次 shuffle”。同时，只测 10 桶无法回答桶数敏感性；把 `20,000 × N` 当成实际 group 数也会误导。

**备选方案**：
- 只保留 `salted: bool`，在文档里口头建议“生产上只给热点 key 加盐”；
- 增加 `salt_scope="hot_only"`，只给指定热点 item 加盐，其余 item 的 `_salt=0`；
- 只改桶数参数，不做多桶测量，继续用理论最大值解释成本。

**最终选择**：实现 `none / all / hot_only` 三种 scope；benchmark 三方案交错运行；新增 `pipelines/benchmark_salt_sweep.py` 测 2 / 5 / 20 桶；group 基数用 `distinct(item_id, _salt)` 实测，同时保留 `max_possible` 作为理论上限。

**实测结果（2026-11-08）**：
- 10 桶：全量加盐实际 group 数 190,924 / 200,000（95.46%），仅热点键加盐 20,009 / 20,009；
- 全量加盐 stage-1 shuffle write 598,054 条，仅热点键加盐 440,708 条，不加盐 440,303 条；
- 仅热点键加盐 wall clock +19.20%、最长 Task +21.05%，明显轻于全量加盐的 +44.77% / +85.53%，但仍未转为收益；
- 2 / 5 / 20 桶 sweep 中，仅热点键加盐的 wall clock 变化分别为 +11.26% / +15.49% / +8.81%，没有出现“桶数越多越快”的单调关系。

**原因**：选择性加盐只拆真正的热点，stage-1 的 group 基数几乎不变，所以额外 shuffle 很小；但只要仍然保留“先加盐、再去盐”的两阶段，在本写法下通常会多一次 shuffle：加盐改变了 stage-1 的 key，阻断了原本可被 Catalyst 合并的同 Key 两阶段聚合。对可 map-side combine 的 `count/sum`，这点固定成本仍然大于被打散长尾的收益。桶数 sweep 也说明：更多桶会增加 group 基数、序列化与调度成本，收益并非单调。

**sweep 口径**：每个桶数都独立重跑了三种方案（包括不加盐 baseline），所以每一行是桶内配对比较。但 baseline 自身在 2.033s–2.211s 之间漂移（10 桶的 2.354s 来自另一份 `benchmark_results.json`，不属于这次 sweep），跨桶比较百分比时，差异里混有 baseline 漂移和单次运行噪声。不能把 20 桶的 +8.81% 与 2 桶的 +11.26% 的差全部归因于桶数本身；sweep 同样只有每个桶 1 个 measured sample，没有做显著性检验。

**代价**：`hot_only` 必须显式传入 `hot_item_id`，需要先用 skew probe 找到热点；桶数 sweep 使 benchmark 运行时间增加（3 个桶 × 3 方案 × 2 次），但这些数字比“只测一个桶数”更可信。该实现仍只适用于单热点 key，不处理多热点或热点集合。
