# 核心设计与技术复盘

本文档是对 SparkSkew-Benchmark 在架构设计、数据质量保障、性能调优及模型评估等环节的深度复盘。记录了开发过程中面临的架构取舍与实测数据，供后续维护或技术评审时参考。

---

## 1. 架构演进与数据分层设计

### 1.1 项目的核心定位与链路
本项目是一个纯本地可执行的 PySpark 电商全链路工程。从原始 CSV 文件出发，实现 ODS -> DWD -> DWS 的三层数仓构建，并在 DWD 层之上产出行为特征与隐式 ALS 推荐模型。同时，针对数据倾斜场景进行了加盐对比实验。项目的核心价值不在于强行调优出一个高 NDCG 指标，而在于验证分层规范、质量门禁、倾斜测试和评估协议的工程可行性。

### 1.2 ODS / DWD / DWS 的职责边界
采用三层架构的核心目的在于解耦“原始事实”与“业务口径”：
*   **ODS (原始数据层)**：原始 CSV 全用 String 类型落 Parquet，附加 `_ingest_ts` 和 `_source_file`，保证数据可追溯、可重放。
*   **DWD (明细数据层)**：执行类型转换、非法行为过滤、按主键去重、按 `dt` 分区，并强制执行 4 条数据质量断言。
*   **DWS (汇总数据层)**：按 item 汇总的宽表，供推荐特征工程和看板对账使用。这样的设计使得 DWD 重算不会污染 ODS，DWS 也可以随时按新口径重建。

### 1.3 接入层类型转换的取舍
ODS 层的核心职责是保留最原始的数据切片。如果在接入层强行转换类型，一旦失败原始文本就会丢失；全存 String 的话，DWD 可以随时重新解释 Schema，也能避免 `inferSchema` 对脏数据静默填充 null。代价是 DWD 层必须显式承担 cast 和过滤的逻辑。

### 1.4 批处理作业的幂等性保障
DWD 层主要依靠两层机制保证幂等：
1.  `dropDuplicates(["user_id","item_id","event_time"])` 确保主键唯一。
2.  `write.mode("overwrite").partitionBy("dt")` 实施全量静态覆盖。
在 `common.py` 中固定了 `partitionOverwriteMode=static`，防止因动态覆盖导致“本次未产出某 dt 但旧数据残留”的脏数据问题。针对全量批处理场景，主键 merge 需要引入增量窗口和水位线，复杂度过高，静态全量覆盖是当前最优解。

## 2. 数据质量门禁与对账机制

### 2.1 DWD 层的核心断言
在 `spark_jobs/dwd_build.py:92-127` 中设定了 4 条核心断言：
1.  非空检查：`row_count > 0`；
2.  主键唯一：distinct 数量等于总行数，duplicates=0；
3.  关键字段（`user_id`、`item_id`、`event_time`、`behavior_type`）非空率 ≥ 0.999；
4.  持久化后的行数与已验证行数一致。

### 2.2 阈值设定 0.999 的考量
在真实生产环境中，要求绝对 1.0 的非空率过于脆弱，少量缺失即可导致整批任务失败。0.999 的阈值允许极少量异常数据存在，同时能敏锐捕捉系统性空值风险。该阈值定义为显式常量 `NON_NULL_THRESHOLD = 0.999`，杜绝魔法数。

### 2.3 DWS 层跨表对账逻辑
DWS 构建完成后执行两条强校验：
1.  DWS 行数 = DWD distinct item 数（实测 20,000 = 20,000）。
2.  `sum(event_count)` = DWD 总行数（实测 1,000,000 = 1,000,000）。
第一条确保维度没有膨胀，第二条确保度量没有丢失。

### 2.4 Fail-fast 机制的设计意图
当对账失败时，`assert_equal` 直接抛出 `AssertionError`。由于 `run_pipeline.py` 未捕获该异常，进程会以非零状态码退出。这属于刻意设计的 Fail-fast 策略：宁可让批处理任务失败报警，也绝不将一个口径不一致的 DWS 表发布给下游。

## 3. Shuffle 性能剖析与 Benchmark 设计

### 3.1 倾斜场景的构造与影响
`groupBy(item_id)` 按哈希分发数据，当热门 item（如 9999）占比达 38.04% 时，单一 reducer 将承受近 38 万行的计算压力。这会导致 Stage 执行时间被该长尾 Task 显著拖慢，极易引发 Spill 甚至 OOM。生成器通过 `--hot-ratio 0.38` 显式构造了这一极限测试场景。

### 3.2 加盐两阶段聚合原理
*   **Stage 1**：执行 `groupBy(item_id, _salt)`，将热门 item 的原始数据打散至 N 个独立的局部小组。
*   **Stage 2**：去除 `_salt`，再次执行 `groupBy(item_id)`，对 Stage 1 的局部结果进行二次聚合。
通过这一架构，Stage 2 每个 item 最多只需处理 N 行（N 为盐桶数）的局部结果，避免了单点压力。

项目实现了三种 `salt_scope`：
*   `none`：不加盐，作为对照；
*   `all`：所有 item 都加盐，用来测“全量加盐”的上界成本；
*   `hot_only`：只给指定的 `hot_item_id` 加盐，其余 item 的 `_salt=0`。这是实际生产中更常见的“选择性加盐”做法，避免为了一个热 key 把 2 万个普通 item 都拆开。

注意：加盐方案在本写法下会多一次 shuffle（stage-1 按 `(item_id, _salt)`，stage-2 才恢复 `item_id`，通常无法享受同 key 两阶段聚合的合并）；不加盐的两次同 key `groupBy` 可能被 Catalyst 合并成一次 shuffle。因此 benchmark 比较的是“加盐这套做法 vs 不加盐”，并明确报告额外 shuffle，而不是声称物理计划只差一个布尔位。

### 3.3 确定性盐值生成策略
盐值计算采用 `pmod(xxhash64(user_id, behavior_type, event_time), N)`。
*   **摒弃 `rand()`**：随机盐值将导致分组结果不可预测，彻底摧毁重复运行对比与 DWS 对账的可行性。
*   **摒弃 `user_id % N`**：单用户频繁操作热门商品时，仍会导致数据向单一桶聚集。
*   **引入 `event_time`**：有效提升 Hash 基数，将同一用户的连续行为彻底打散。

### 3.4 盐桶数量的估算模型
经验公式为 `N ≈ ceil(hot_key_rows / target_rows_per_task)`。项目中 38 万热门行，目标单 task 处理 3.8 万行，故 N 取 10。盲目增大 N 会引发 Stage 1 的 group 基数急剧增加，序列化开销与 Shuffle IO 显著增加。生产环境需结合分区数与单 task 内存上限动态调整。

实际 group 数不是简单的 `20,000 × N`。10 桶时全量加盐实测 distinct `(item_id, _salt)` 为 **190,924**，而理论上限是 200,000；5 桶实测 99,799 / 100,000，20 桶实测 315,405 / 400,000。Hash 碰撞会让实际值低于上限，所以文档同时给出 `actual` 和 `max_possible`，不拿理论上限当实测值。

### 3.5 实测结果与成本模型验证
（环境：1M 行，local[8]，16 分区，AQE off；2026-11-08 measured run 2）

| 聚合方案（10 桶） | Wall Clock | 最长 Task | Shuffle Write | Stage-1 实际 group |
|---|---:|---:|---:|---:|
| 不加盐 | 2.354s | 456ms | 10.630MB | 20,000 |
| 全量加盐 | 3.408s | 846ms | 18.418MB | 190,924 |
| 仅热点键加盐 | 2.806s | 552ms | 11.522MB | 20,009 |

**结论（仅限本实验条件）**：在上述 1M 行、`local[8]`、16 分区、AQE off 的 `count/sum` 负载下（支持 map 端 Combine），本实现里的两种加盐方式都产生了负优化。不加盐时，100 万行数据在 map 端已被 Combine 压缩至约 44 万条 Shuffle 记录，reduce 端未出现长尾；全量加盐把 stage-1 的 group 数扩大到实测 190,924，并额外引入一次 Shuffle，导致整体性能下降。仅热点键加盐只把 item 9999 拆成 10 个桶，stage-1 group 数为 20,009、shuffle write 为 440,708 条，额外开销明显变小，wall clock 变化从全量加盐的 +44.77% 降到 +19.20%，但因为在本写法下仍多一次 shuffle，没有转为收益。该负结果已如实记录于工程文档中；它不能外推到生产规模或开启 AQE 的环境。

桶数 sweep 进一步显示：2 / 5 / 20 桶下，全量加盐 wall clock 变化为 +14.25% / +37.14% / +34.79%，仅热点键加盐为 +11.26% / +15.49% / +8.81%。每个桶的 baseline 都是桶内独立重跑，但本轮单次 sweep 未观察到“桶数越多越快”的单调关系；跨桶百分比差异仍混有 baseline 漂移（2.033s–2.211s）和单次运行噪声，不能全部归因于桶数。

本实验最长 Task 只有 456ms，长尾并不严重；“仅热点键加盐仍为负”只适用于这份实现和负载；Join 倾斜或 groupByKey 长尾、单 Task 达到数千万行时，加盐仍可能有效，但必须实测净收益。

### 3.6 加盐技术的适用边界

加盐不是“不可 Combine 就一定有效”。不可 Combine 只说明 baseline 无法在 map 端把热 key 压小，是加盐**可能**有效的必要条件，不是充分条件；额外 shuffle、group 基数膨胀、第二阶段是否仍倾斜，都会影响净收益。以下场景值得优先验证，但必须用 skew probe 和实测指标确认：

*   聚合操作不可 map-side combine（如 `collect_list`、`collect_set`、精确去重、复杂 percentile）。
*   大表 join 时出现极端的单 key 热点。
*   单分区数据量严重超出 executor 内存。

若聚合本身支持 Combine，应优先交由 Spark 内部处理。如果确实只有少数热点 key，优先使用 `hot_only` 而不是全量加盐：前者只增加少量 stage-1 group，额外 shuffle 明显更小；但它仍然不是免费的，是否值得要看 skew probe 和实测。本项目只在 `count/sum` 负载上实测了负结果，**没有对上述不可 Combine 场景做实证**，不能拿本项目的结果替它们背书。

### 3.7 Benchmark 变量控制原则
*   **固定 16 个 Shuffle 分区**：控制变量，确保对比公平。
*   **关闭 AQE**：AQE 的自适应特性（如 Skew Join 处理）会掩盖真实的倾斜状况，关闭后方可观测原始 Shuffle 行为。
*   **交错执行与预热（U1, F1, H1, U2, F2, H2）**：仅取每种方案第二次运行结果，避免 JVM 启动、JIT 编译与缓存预热带来的指标失真。
*   **单样本口径**：每种方案只有 1 个进入统计的 measured sample；表中百分比是单次运行差异，没有重复采样、置信区间或显著性检验。Shuffle records / group 基数 / Task 数是结构指标，方向比 wall clock 百分比更稳。
*   **实际 group 基数与理论上限分开报告**：用 `distinct(item_id, _salt)` 现场测量，不把 `distinct_items × N` 当成实测值。
*   **采用 `.collect()` 触发**：避免 `.count()` 触发 Catalyst 优化导致聚合阶段被跳过，强制物化 2 万行局部结果，确保两阶段计划完整执行。

### 3.8 深度 Task 指标的采集方案
PySpark 3.5 缺乏 Python 侧的 Listener 支持。项目采用 Java 编写 `TaskTimingCollector extends SparkListener`，在 `onTaskEnd` 事件中提取 `TaskInfo.duration()` 及 Shuffle 读写指标。若编译失败，系统自动降级为 `fallback_total_time_only` 模式，仅记录 Wall Clock，绝不伪造 Task 级数据。

## 4. 推荐模型选型与评估协议

### 4.1 隐式 ALS 的选型依据
日志仅包含 pv/cart/fav/buy 行为，缺乏 1-5 星显式评分。将行为映射为分数缺乏业务逻辑支撑，且“未点击”绝对不能等价于“0 分”（可能是未曝光）。隐式 ALS 将行为权重转化为置信度，优化目标与 Top-K 排序逻辑高度契合。

### 4.2 置信度构造与模型参数
按 `(user_id, item_id)` 聚合行为权重：`pv=1, fav=2, cart=3, buy=5`，求和作为 `rating`。设置 `alpha=40` 控制置信度放大系数。核心参数：`implicitPrefs=True`、`rank=32`、`maxIter=10`、`regParam=0.08`。

### 4.3 时间切分策略的严格性
采用按 `event_time` 的 80% 分位点进行严格切分（训练集 `<= 切分点`，测试集 `> 切分点`）。此举旨在杜绝随机切分导致的“未来行为泄漏至训练集”问题，真实模拟工业界“用历史预测未来”的部署场景。

### 4.4 冷启动处理与兜底评估
测试期出现的冷启动用户无法由 ALS 打分，系统将其从主评估集剔除，并单独报告其比例（占比 11.09%）。同时，采用训练期热门商品进行 popularity 兜底，单独评估，严禁与 ALS 指标混淆。

### 4.5 已见商品过滤机制
推荐系统需具备“探索”能力，将训练集中已交互过的商品再次推荐违背了泛化原则。在 `build_predictions()` 中通过 left anti join 剔除 `seen` 集合，仅对未见候选进行排序。

### 4.6 排序指标的选择与 RMSE 的局限性
隐式反馈缺乏可靠的负样本，强行计算 RMSE 会在业务解释上产生严重偏差。系统采用 NDCG、MAP、Precision、Recall 评估 Top-K 列表质量。**隐式反馈不适用 RMSE** 是本项目评估阶段的核心底线。

### 4.7 离线指标的真实水位与原因剖析
实测 K=10 指标：NDCG@10 为 0.000963，MAP@10 为 0.000716。
指标偏低源于合成数据的随机性：非热门商品呈均匀分布，缺乏协同信号；热门商品几乎被所有训练用户曝光，按协议被剔除。模型本质是在随机商品中进行排序，指标接近随机属数据特性，评估逻辑无误。

### 4.8 模型优化的可行演进方向
若需提升业务指标，优化路径应包括：
1.  注入业务规则：在生成器中植入用户偏好，构造真实协同信号。
2.  引入内容特征：实施 content-based 模型或冷启动模型。
3.  升级召回算法：引入负采样 + BPR 或序列模型（如 SASRec）。
4.  完善 Baseline 对照：补充 popularity/random 基线，量化真实提升幅度。

## 5. 特征工程与防泄漏

### 5.1 行为序列特征构造
`evaluation/features.py` 基于用户分组及时间排序，利用 `lag` 提取时序特征，涵盖行为转移计数、事件时间间隔、频次及多样性等。输出 17 维用户特征与 10 维商品特征。类目特征经 `StringIndexer` 处理，避免离散 ID 被误认为连续数值。

### 5.2 数据泄漏防护机制
当前 ALS 评估仅依赖 DWD 底表，未使用特征表。特征表为全量构建，当前仅用于探索性分析与兜底策略设计。若后续接入监督式模型，必须在训练时间窗内严格重建特征集，该限制已在文档中显著标注。

## 6. 架构演进与工程化扩展

### 6.1 运行时环境隔离
鉴于 Spark 3.5.1 对 Java 21 的兼容性限制，项目采用内置便携版 Temurin JDK 17 与 winutils。此策略杜绝了对系统 `JAVA_HOME` 的污染，保障了多项目环境隔离。

### 6.2 规模化扩展至 10 亿级数据的演进路径
若数据量跃升至十亿级，架构需进行如下重构：
*   **输入与 DWD**：启用按日期/小时分区，执行增量重处理，摒弃全量 overwrite。
*   **Shuffle 层**：动态调整 `spark.sql.shuffle.partitions`，避免长尾。
*   **模型层**：引入 checkpoint，候选生成必须替换为 ANN/向量检索。
*   **评估层**：实施采样评估或离线分桶，防止 Driver 端 OOM。

### 6.3 边界说明与未验证项声明
*   未在真实集群环境（YARN/K8s）进行集群级验证。
*   本项目 1M 行、单向 Shuffle 约 10.6MB，量级远低于本机内存上限；benchmark 没有采集 Spill 字段，也没有观察到 Spill/OOM。它是机制验证，不是更大数据量下 Spill/OOM 事故的复现。
*   未接入线上真实曝光日志，缺乏 A/B 测试数据。
*   UI 层未进行全链路浏览器视觉回归，仅通过 AppTest 无头验证。
*   未配置 CI/CD 流水线及 Release 流程。
*   缺乏显式评分数据集，无法提供 RMSE 对照。
